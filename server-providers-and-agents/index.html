Where do agents actually run?

A map of the companies that rent computing — and the new layer being built on top of them specifically to host AI agents.

In one sentence — what are these companies called?

They're cloud service providers (CSPs) — companies that rent computing capability (compute, storage, networking, and progressively more of the software stack) on demand and pay-as-you-go, so you consume infrastructure as a service instead of owning and operating it. The largest, spanning every layer, are the hyperscalers (AWS, Azure, GCP).

The “as-a-service” spectrum

Every cloud offering sits on one axis: where the managed boundary falls in the stack. The lower you go, the more you control and the more you operate yourself; the higher you go, the less you manage — at the cost of flexibility, portability, and the ability to run long-lived processes. Each tier hands one more responsibility layer to the provider. Most real 2026 architectures composite several tiers rather than picking one.

03

What an agent needs that a website doesn’t

A website is request-driven: code runs only when someone calls it, then dies. An agent acts on its own initiative and lives for hours-to-days across crashes and human waits. These nine capabilities are what turn “a server” into “a place an agent can live.”

01

Always-on / scheduled loop

A resident process or durable wake-trigger that runs with no user request in flight. Without it there’s no agency — only an API someone else calls.

Served bySupervised process (systemd / Docker restart:unless-stopped / k8s) — not a bare OS boot-task. Or managed worker tiers (Modal, Durable Objects, Inngest).
02

Durable execution

Exactly-once external side effects across crashes, restarts, and long human waits. A naive retry double-sends the email; a crash loses hours of reasoning. The clearest line between an app and an agent.

Served byTemporal · Restate · DBOS · Inngest — append-only journal + idempotency keys → replay-after-crash, skip committed effects.
03

Persistent + semantic memory

Structured durable state (what’s pending, what was decided) and embeddings-based recall over an open-ended corpus, so a fresh-context run can reconstruct “what did we do last time.”

Served byPostgres/SQLite + a vector store — pgvector, Qdrant, Pinecone, Weaviate, LanceDB — behind an embeddings model.
04

Sandboxed code execution

Agents write and run code and process untrusted input. That code can be wrong, hostile, or prompt-injected — it must run in an isolation boundary that can’t read secrets or persist, and that you can kill cheaply.

Served bymicroVM/container sandboxes — E2B (Firecracker), Modal, Daytona, or self-hosted Firecracker/gVisor/Kata.
05

Tool / MCP gateway + secrets

An agent’s reach into real systems must be brokered, not handed raw: centralized tool discovery, scoping, per-account routing, audit — with OAuth tokens kept out of prompts and code.

Served byAn MCP gateway with identity-based routing + tool-gating; a secrets vault (Vault, cloud Secret Manager, Proton Pass CLI) injected at runtime.
06

Human-in-the-loop surface

Autonomy without a brake is the dominant failure mode. The agent proposes, freezes the payload durably, and nothing ships until a human accepts/revises/dismisses — even across a multi-day wait.

Served byA queue + UI bound to the durable engine — a dashboard (accept/revise/dismiss) and/or Slack/Telegram approvals; “accepted” unfreezes the send.
07

Durable scheduling / cron

Proactive cadence is the agent’s heartbeat. The schedule must survive restarts and be idempotent — a missed tick or a double-fire must not double-act. Cadence is also the cost dial.

Served byDurable timers inside the engine (Temporal/Restate/Inngest), or a managed scheduler / k8s CronJob with a concurrency guard.
08

Observability & tracing

Agents are non-deterministic and act unattended — “is it healthy?” can’t be an HTTP 200. You need per-run traces of reasoning, every tool call, latency, retries, and token/cost per step.

Served byOpenTelemetry → an LLM-obs backend (Arize Phoenix, Langfuse, LangSmith, Helicone) + a cost ledger and spend-cap circuit-breaker.
09

Governed egress to model APIs

The model is the agent’s cognition; every step is a remote inference call needing retry/backoff, a budget guard, and key governance. For a website this path doesn’t exist; for an agent it’s the critical path.

Served byProvider SDKs or an LLM gateway (LiteLLM, OpenRouter, Portkey, Cloudflare AI Gateway) for failover, caching, and spend limits.

The new layer: agent infrastructure

Because agents have demands ordinary apps don’t, a 2026 layer of products has emerged on top of the generic stack — built specifically to host AI agents.

Durable execution has crossed into early-majority adoption (Temporal’s $300M Series D at a $5B valuation; AWS, Cloudflare, and Vercel all shipping workflow primitives), and the big clouds reached GA on managed agent runtimes between Q4 2025 and Q1 2026. Control vs convenience vs cost vs lock-in

Choosing where to host an agent is a four-way tension. Self-hosting on IaaS maximises control and residency but you build durable execution, sandboxes, and observability yourself. Managed agent platforms invert it — convenience by SDK call, but your data flows through their plane, costs escalate as agents do real work, and you take on lock-in to proprietary runtimes.

AO v1 sits top-left: self-hosted control, building its own agent-infra layer.

The pragmatic answer is a split stack matched to risk: keep the irreversible and secret-bearing parts close, rent the elastic and undifferentiated parts. Pick durable-execution and gateway layers with portable APIs so the expensive core stays movable — and let cadence (ticks/day) be the cost dial you tune against a hard spend cap.

Keep close ⟵ control
  • Secrets & OAuth tokens
  • The human-approval surface
  • Credential routing / MCP gateway
  • The durable journal of side effects
Rent ⟶ convenience
  • Sandbox compute (per-task)
  • Embeddings / vector recall
  • Model egress via a swappable gateway
  • Browser fleets, GPU bursts

Where AgenticOS v1 sits on this map

Self-hosted IaaS — and it builds the agent-infra layer itself

build, don’t buy

AO v1 doesn’t rent a managed agent platform. It runs the loop on a self-hosted box (a Synology NAS today, an EU cloud VM next) and assembles the “agent infrastructure” layer from open, portable parts — which is why the build-vs-buy ruling parked an off-the-shelf engine and chose native. That keeps every secret-bearing, irreversible part inside your own boundary while staying movable.
